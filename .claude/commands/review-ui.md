## 리뷰 범위

버그나 로직 정확성이 아니라, 사용자가 화면에서 실제로 겪을 경험에 집중하세요. 다음 항목을 순서대로 점검하세요.

1. **접근성**
   - 인터랙티브 요소(버튼, 링크, input)에 적절한 시맨틱 태그와 `aria-label` 등이 있는지
   - 폼 입력에 `<Label htmlFor>` 연결이 되어 있는지
   - 키보드만으로 조작 가능한지 (포커스 순서, `focus-visible` 스타일)
   - 색상만으로 상태를 전달하지 않는지 (에러 메시지에 텍스트도 있는지)

2. **반응형 레이아웃**
   - 모바일 너비에서 레이아웃이 깨지지 않는지 (`sm:`, `md:` 브레이크포인트 사용 여부)
   - 고정 너비/높이로 인해 작은 화면에서 잘리는 요소가 없는지
   - 터치 타겟 크기가 충분한지

3. **다크모드 일관성**
   - 하드코딩된 색상(`text-black`, `bg-white` 등) 대신 시맨틱 토큰(`text-foreground`, `bg-background`, `text-muted-foreground` 등)을 쓰는지
   - 다크모드에서 대비가 충분한지

4. **디자인 일관성**
   - `src/components/ui`의 기존 컴포넌트(Button, Card, Badge 등)를 재사용하는지, 새로 임의 스타일을 만들지 않는지
   - 간격(spacing), 타이포그래피 스케일이 프로젝트의 기존 패턴과 일치하는지
   - 로딩 상태(`Skeleton`), 빈 상태, 에러 상태가 고려되어 있는지

5. **사용자 흐름**
   - 폼 제출 중 중복 클릭 방지(`disabled={isSubmitting}` 등)가 되어 있는지
   - 액션에 대한 피드백(토스트, 에러 메시지)이 있는지
   - 네비게이션 활성 상태(active state)가 명확한지

## 출력 형식

- 버그 리포트처럼 나열하지 말고, 항목별로 "문제 → 왜 사용자 경험에 영향을 주는지 → 구체적 수정 제안"을 간결하게 작성하세요.
- 파일명과 줄 번호를 `file.tsx:12` 형식으로 포함하세요.
- 문제가 없는 항목은 굳이 언급하지 마세요.
- 코드를 직접 수정하지 말고 리뷰만 제공하세요. 사용자가 수정을 요청하면 그때 적용하세요.
